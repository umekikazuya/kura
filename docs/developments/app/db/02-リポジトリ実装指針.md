# 02. リポジトリ実装指針

> `ClipItemRepository` インターフェースの各メソッドが実行する SQL を定義する。
> 本ドキュメントはインフラ層（SQLite 実装）の実装者向けガイドである。
> すべてのクエリはプリペアドステートメントで実行し、SQL インジェクションを防止する。

---

## 1. メソッドと SQL のマッピング

### `FindByID(id ClipItemId) (*ClipItem, error)`

```sql
SELECT
    id, content, content_hash, type, image_path,
    source_app_bundle_id, source_app_name,
    is_pinned, is_truncated, created_at, updated_at
FROM clips
WHERE id = :id
LIMIT 1;
```

---

### `FindByHash(hash ContentHash) (*ClipItem, error)`

重複チェック（UC-01）で使用する。

```sql
SELECT
    id, content, content_hash, type, image_path,
    source_app_bundle_id, source_app_name,
    is_pinned, is_truncated, created_at, updated_at
FROM clips
WHERE content_hash = :content_hash
LIMIT 1;
```

> `content_hash` には UNIQUE 制約があるため、結果は 0 件または 1 件のみ。

---

### `FindRecent(limit int) ([]*ClipItem, error)`

空クエリ時のデフォルト表示に使用する。ピン留めアイテムを先頭に表示する。

```sql
SELECT
    id, content, content_hash, type, image_path,
    source_app_bundle_id, source_app_name,
    is_pinned, is_truncated, created_at, updated_at
FROM clips
ORDER BY is_pinned DESC, updated_at DESC
LIMIT :limit;
```

---

### `Search(query string, limit int) ([]*ClipItem, error)`

FTS5 による全文検索。ピン留めアイテムを先頭に表示する。

```sql
SELECT
    c.id, c.content, c.content_hash, c.type, c.image_path,
    c.source_app_bundle_id, c.source_app_name,
    c.is_pinned, c.is_truncated, c.created_at, c.updated_at
FROM clips c
INNER JOIN clips_fts fts ON c.id = fts.content_id
WHERE clips_fts MATCH :query
ORDER BY c.is_pinned DESC, rank
LIMIT :limit;
```

**`:query` の前処理**:
FTS5 の特殊文字（`"`, `*`, `(`, `)` 等）をエスケープしてから渡す。
ユーザー入力は `"<input>"` のようにダブルクォートで囲む。

**性能要件**: 10万件データに対して 10ms 以内。

---

### `Save(item *ClipItem) error`

新規保存（INSERT）と状態変更の反映（UPDATE）を兼ねる。
`ClipItem` が新規か既存かの判断はアプリケーション層が行い、Repository は `item` の状態をそのまま永続化する。

**新規保存（INSERT）**:

```sql
INSERT INTO clips (
    id, content, content_hash, type, image_path,
    source_app_bundle_id, source_app_name,
    is_pinned, is_truncated, created_at, updated_at
) VALUES (
    :id, :content, :content_hash, :type, :image_path,
    :source_app_bundle_id, :source_app_name,
    :is_pinned, :is_truncated, :created_at, :updated_at
);
-- トリガー trg_clips_after_insert が clips_fts を自動更新
```

**状態変更の反映（UPDATE）**:

`RefreshTimestamp()` 後の再コピー、または `Pin()` / `Unpin()` 後のピン留め変更に使用する。
`is_pinned` の値はアプリケーション層が集約メソッドを通じて確定済みであり、
Repository は受け取った値をそのまま書き込む（DB 側でトグル判断を行わない）。

```sql
UPDATE clips
SET
    is_pinned  = :is_pinned,
    updated_at = :updated_at
WHERE id = :id;
```

---

### `Delete(id ClipItemId) error`

```sql
DELETE FROM clips WHERE id = :id;
-- トリガー trg_clips_after_delete が clips_fts を自動削除
```

## 2. トランザクション設計

### UC-01: クリップ記録トランザクション

重複チェック（READ）と INSERT/UPDATE（WRITE）を1トランザクションに包み、
検知と保存の間に別の書き込みが割り込まないことを保証する。

```
BEGIN IMMEDIATE;
  1. FindByHash(:hash)                       -- 重複チェック
  2a. (結果なし) Save(新規 ClipItem)         -- INSERT
      データ保持ポリシーの超過チェック・削除
  2b. (結果あり) Save(RefreshTimestamp 済み) -- UPDATE updated_at
COMMIT;
```

**`BEGIN IMMEDIATE` を使用する理由**:
WAL モード下でも書き込みロックを即時取得し、`SQLITE_BUSY` の発生を最小化する。

### UC-05: 削除トランザクション

```
BEGIN;
  Delete(:id);
  -- トリガーが clips_fts からも削除（同一トランザクション内）
COMMIT;
```

## 3. エラーハンドリング

| エラー | 対処 |
|:---|:---|
| `SQLITE_BUSY` | 最大3回、50ms 間隔でリトライする |
| `SQLITE_CONSTRAINT_UNIQUE` | `content_hash` の重複。アプリケーション層のロジック不備として上位にエラーを返す |
| `SQLITE_FULL` | ディスク容量不足。ログ記録後、非ピン留めの最古100件を削除して1回だけ再試行する |
| レコード不存在 | `FindByID` / `FindByHash` が 0 件の場合は `nil, nil` を返す（エラーではない）|
