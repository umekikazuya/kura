# 01. OS 統合設計

> kura が macOS と直接対話するインフラ層の設計を定義する。
> クリップボード入力（NSPasteboard 監視）とペースト出力（CGEvent）の2つのI/Oを扱う。

---

## 1. クリップボード入力：NSPasteboard 監視

### 1.1 監視方式の選択

実装の複雑さを避けるため、独自に CGO や Objective-C を記述することは避け、**Wails の標準機能（または実績のある Go ライブラリ）** を優先して使用する。

| 方式                               | 概要                                                                               | 採用判断                                                                         |
| :--------------------------------- | :--------------------------------------------------------------------------------- | :------------------------------------------------------------------------------- |
| **Wails Runtime API** (ポーリング) | `runtime.ClipboardGetText()` 等を一定間隔（例: 500ms）で呼び出して変更を検知する。 | **第1候補**。保守性が最も高い。適度な間隔にすることでCPU負荷を許容範囲に抑える。 |
| **Go ライブラリ** (イベント駆動)   | `golang-design/clipboard` 等の OS イベントをラップしたライブラリを使用する。       | 第2候補。Wails のポーリングでパフォーマンス要件を満たせない場合に検討。          |
| **独自 CGO (CFRunLoop)**           | 自前で Objective-C を書いて Go と繋ぐ。                                            | 原則として使用しない。                                                           |

### 1.2 変更検知の仕組み

Go の Goroutine 内で一定間隔でクリップボードの内容を確認する。
前回の取得内容と比較し、差分があれば `RecordClipUseCase` へ委譲する。

```text
Goroutine (Wails API で定期確認)
    ↓ 変化を検知
Go チャネル（バッファサイズ 1）
    ↓
RecordClipUseCase へ委譲
```

バッファサイズ 1 のチャネルを使うことで、連打（バースト）時の二重処理を防ぐ。

### 1.3 ConcealedType の検出

`org.nspasteboard.ConcealedType` が UTI リストに含まれるかを監視側で検査し、
検出した場合はアプリケーション層に渡す前に即時棄却する。
この判断はインフラ層の責務であり、ドメイン層には届かない。

### 1.4 Goroutine の安全性

| 問題                       | 対策                                                  |
| :------------------------- | :---------------------------------------------------- |
| バースト（高速連続コピー） | バッファサイズ 1 のチャネルで吸収。後続イベントは無視 |
| アプリ終了時               | `context.WithCancel` で監視 Goroutine を安全に停止    |

> IO 層は `RecordClipUseCase` を呼ぶだけであり、`ClipItemRepository` を直接知らない。Repository との排他制御はアプリケーション層・インフラ実装層の責務。

## 2. ペースト出力：CGEvent

選択したクリップをユーザーの直前のアクティブアプリへ送信する。

### 2.1 ペースト実行フローと自己記録の防止

kura 自身がペーストを行う際、OS のクリップボードにデータを書き込むため、自身の監視機能がそれを「新規コピー」として誤検知してしまう（**自己記録問題**）。
これを防ぐため、書き込み直前に「無視フラグ（ignoreNextChange）」を立てる。
※ 監視処理（別 Goroutine）とのデータ競合を防ぐため、このフラグは `atomic.Bool` または `sync.Mutex` を用いてスレッドセーフに実装する。

**ペースト操作のフロー**:

```text
1. ignoreNextChange.Store(true) （次回検知スキップフラグをオン）
2. ClipItem.content を OS クリップボード（Wails API経由等）にセット
3. Wails.WindowHide() でウィンドウを非表示
4. CGEvent で Cmd+V をエミュレートして直前のアプリへ送信
※ ステップ3や4で回復不能なエラーが起きた場合は、defer 等で確実に ignoreNextChange.Store(false) を実行し、フラグがスタックして以後の正規のコピーが無視されることを防ぐ。
```

**監視プロセスの対応**:

```go
// クリップボード変更検知時
if ignoreNextChange.Load() {
    ignoreNextChange.Store(false)
    // 自分がペーストのためにセットしたデータなので、記録処理をスキップ
    return
}
```

### 2.2 アクセシビリティ権限

CGEvent の送信には macOS のアクセシビリティ権限が必要。
アプリ起動時に `AXIsProcessTrusted()` で権限を確認し、未許可の場合はシステム設定へ誘導する。

権限がない場合の挙動:

- ペースト機能のみ無効化
- クリップボード監視・履歴管理・検索は継続動作

## 3. ファイル I/O

> **パスの使い分け方針**:
> ユーザーが編集する設定ファイルは `~/.config/kura/`、アプリが管理するデータ（DB・画像）は `~/Library/Application Support/kura/` に分離する。

### 3.1 画像キャッシュ

`type = "image"` のクリップは、バイナリを PNG ファイルとしてローカルに保存する。

- 保存先: `~/Library/Application Support/kura/images/<uuid>.png`
- サイズ上限: 20MB（超過時は切り詰め、`Content.truncated = true`）

### 3.2 設定ファイル

- 配置: `~/.config/kura/config.json`
- 変更検知: `fsnotify` でファイル監視し、アプリ再起動なしに即時反映
