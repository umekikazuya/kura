# 02. ユースケース

> 各ユースケースはアプリケーション層（UseCase）に対応する。
> アプリケーション層はドメインオブジェクト（Repository・Factory・DomainService）を
> 組み合わせてユースケースを実現するが、ドメインロジック自体は持たない。
> ストレージ実装（SQLite・FTS5）・UI フレームワーク（Wails）の詳細はここに登場しない。

## 2. ユースケース詳細

### UC-01: クリップを記録する

**アクター**: システム（インフラ層の監視プロセス）

**トリガー**: OS クリップボードの変更通知（インフラ層が検知し、アプリケーション層に委譲する）

**事前条件**: アプリが起動中

**基本フロー**:

1. インフラ層がクリップボードの変更を検知する。ConcealedType フラグが付いていればこの時点で棄却し、アプリケーション層には渡さない。
2. インフラ層が生のコンテンツ・型・ソースアプリ情報を `RecordClipUseCase` に渡す。
3. `sourceApp` が非 nil の場合、`sourceApp.IsBlocked(blockedBundleIds)` で除外判定を行う。`true` なら棄却。
4. `ClipItemRepository.FindByHash(hash)` で重複を確認する。
   - **重複あり（再コピー）**: 既存の `ClipItem` を取得し、`item.RefreshTimestamp()` を呼んだ後、`Repository.Save(item)` で更新する。処理終了。
   - **重複なし（新規）**: 次ステップへ。
5. `ClipItemFactory.NewClipItem(rawContent, clipType, sourceApp)` で新しい `ClipItem` を生成する。
6. `ClipItemRepository.Save(item)` で永続化する。
7. インフラ層（Wails IPC）経由でフロントエンドに変更を通知する。

**代替フロー**:

- 1a. ConcealedType 検出 → インフラ層が即時棄却。ログにも記録しない。
- 3a. `sourceApp.IsBlocked()` が `true` → 棄却。処理終了。
- 5a. `NewClipItem` がサイズ超過を検知した場合 → コンテンツを切り詰めて続行（`Content.truncated = true`）。

**ドメインルール**:
- ConcealedType の除外はインフラ層の責務。OS 固有の概念はドメインに届かない。
- 除外アプリの判定は `SourceApp.IsBlocked()` が担う。アプリケーション層は判定ロジックを持たない。
- 重複判定は `ContentHash` の一致で行う。内容が同一なら新規レコードを作らない。

### UC-02: クリップ履歴を検索する

**アクター**: ユーザー

**トリガー**: 検索ボックスへのキー入力

**事前条件**: ウィンドウが表示されている

**基本フロー**:

1. ユーザーが検索ボックスに文字を入力する。
2. フロントエンドがキー入力ごとに即時 `SearchClipsUseCase` を呼び出す。
3. `SearchClipsUseCase` は `ClipItemRepository.Search(query, limit=50)` を呼ぶ。
   - `query` が空の場合は `ClipItemRepository.FindRecent(limit=50)` を呼ぶ。
4. `[]*ClipItem` を受け取り、フロントエンド用の DTO（`[]ClipItemDTO`）に変換して返す。
5. フロントエンドがリストを再描画する。

> **実装の詳細はアプリケーション層が知らない**: `Search()` の内部でどのような全文検索エンジンが使われているかは Repository の実装が決める。アプリケーション層は「クエリを渡せば ClipItem のリストが返る」という事実のみを知る。

**性能要件**: 10万件データに対し、クエリ発行〜DTO 変換完了まで **16ms 以内**（60fps）

### UC-03: クリップをペーストする

**アクター**: ユーザー

**トリガー**: 選択アイテム上での確定操作（Enter キー）

**事前条件**: ウィンドウが表示されていて、1件以上のアイテムが選択されている

**基本フロー**:

1. フロントエンドが選択アイテムの `ClipItemId` を `PasteItemUseCase` に渡す。
2. `PasteItemUseCase` は `ClipItemRepository.FindByID(id)` で `ClipItem` を取得する。
3. アイテムが存在しない場合はエラーを返す。
4. `ClipItem.content` をインフラサービス（`ClipboardWriter`）に渡してクリップボードにセットする。
5. ウィンドウを非表示にする（インフラ層の `WindowService`）。
6. インフラサービス（`PasteEmitter`）が直前のアクティブアプリへペースト操作を送信する。

**事後条件**: 対象アプリにコンテンツがペーストされる。

### UC-04: クリップをピン留めする

**アクター**: ユーザー

**トリガー**: ピン留めキーバインド

**基本フロー**:

1. フロントエンドが対象の `ClipItemId` を `TogglePinUseCase` に渡す。
2. `TogglePinUseCase` は `ClipItemRepository.FindByID(id)` で `ClipItem` を取得する。
3. `item.isPinned == false` の場合: `item.Pin()` を呼ぶ。
4. `item.isPinned == true` の場合: `item.Unpin()` を呼ぶ。
5. `ClipItemRepository.Save(item)` で状態を永続化する。
6. フロントエンドに更新を通知する。

**ドメインルール**: `Pin()` / `Unpin()` は集約ルートのメソッドが不変条件を保護する。
アプリケーション層は状態を直接書き換えない。

---

### UC-05: クリップを削除する

**アクター**: ユーザー

**トリガー**: 削除キーバインド（`Cmd+Backspace` / `dd`）

**基本フロー**:

1. フロントエンドが対象の `ClipItemId` を `DeleteItemUseCase` に渡す。
2. `DeleteItemUseCase` は `ClipItemRepository.Delete(id)` を呼ぶ。
3. フロントエンドに削除完了を通知する。

**ドメインルール**: 削除はリポジトリに委譲する。集約自身は削除処理を知らない。

---

### UC-06: ウィンドウを表示・非表示する

**アクター**: ユーザー

**トリガー**:

- 表示: グローバルショートカット（`Cmd + Option + V`）
- 非表示: `Esc` / `Ctrl + C`

**基本フロー（表示）**:

1. インフラ層（`GlobalShortcutListener`）がショートカットを検知し `ShowWindowUseCase` を呼ぶ。
2. `ShowWindowUseCase` はウィンドウを最前面に表示する（インフラ層 `WindowService`）。
3. 検索ボックスにフォーカスを移す。
4. 直前の検索状態・選択インデックスをリセットする。

**基本フロー（非表示）**:

1. キー入力を検知し `HideWindowUseCase` を呼ぶ。
2. `HideWindowUseCase` はウィンドウを非表示にする。
3. インメモリの検索結果キャッシュを破棄する。

**性能要件**: ショートカット押下からウィンドウ描画まで **32ms 以内（2フレーム以内）**。

### UC-07: 設定を読み込む

**アクター**: システム

**トリガー**: アプリ起動時、または設定ファイルの変更検知

**基本フロー（起動時）**:

1. `LoadConfigUseCase` が設定ファイルを読み込む（インフラ層 `ConfigReader`）。
2. ファイルが存在しない場合はデフォルト値で初期化し、ファイルを新規作成する。
3. 読み込んだ `blockedBundleIds` から `ClipFilteringPolicy` を構築する。
4. 設定ファイルの変更監視を開始する（インフラ層）。

**基本フロー（変更検知時）**:

1. インフラ層がファイル変更を検知し `ReloadConfigUseCase` を呼ぶ。
2. 設定を再読み込みし、`ClipFilteringPolicy` を再構築する。
3. アプリ再起動なしに即時反映する。

> **ドメインへの影響**: 設定コンテキストの変更はアプリケーション層が `ClipFilteringPolicy` を再構築することでコアドメインに伝播する。コアドメインは設定コンテキストの存在を直接知らない。
