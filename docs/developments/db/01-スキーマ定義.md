# 01. スキーマ定義

> kura が使用する SQLite データベースの物理スキーマを定義する。
> スキーマは DBML で記述し、dbdiagram.io で ER 図として可視化できる。
> データベースファイルの配置: `~/Library/Application Support/kura/kura.db`

---

## 1. DBML スキーマ

> DBML (Database Markup Language): https://dbml.dbdiagram.io/docs/
> ER 図の確認: https://dbdiagram.io に以下の DBML を貼り付ける。

```dbml
Table clips {
  id                   text    [pk, note: 'UUID v7: 時刻順ソート可能']
  content              text    [not null, note: 'テキストの場合は本文。type="image" の場合は空文字列']
  content_hash         text    [not null, unique, note: 'SHA-256 hex (64文字)。重複検出キー。ClipItem.contentHash に対応']
  type                 text    [not null, note: '"text" | "image" | "file"']
  image_path           text    [note: 'type="image" の場合のみ非 NULL。~/Library/Application Support/kura/images/ 配下']
  source_app_bundle_id text    [note: 'SourceApp.bundleId。reverse-DNS 形式 (例: com.apple.Safari)']
  source_app_name      text    [note: 'SourceApp.name。表示用']
  is_pinned            integer [not null, default: 0, note: '0=通常 / 1=ピン留め。ClipItem.isPinned に対応']
  is_truncated         integer [not null, default: 0, note: '0=完全 / 1=ペイロード制限により切り詰め済み。Content.truncated に対応']
  created_at           integer [not null, note: 'UNIX epoch 秒。生成時に確定し変更しない']
  updated_at           integer [not null, note: 'UNIX epoch 秒。再コピー（RefreshTimestamp）時のみ更新']
}

// FTS5 仮想テーブルは DBML で表現できないため §2 に SQL で記述する。
// clips_fts は clips.id を content_id として参照するが、
// SQLite の仮想テーブルは外部キー制約を持たない。
```

**ドメインモデルとのマッピング**:

| DB カラム              | ドメイン             | 備考                                |
| :--------------------- | :------------------- | :---------------------------------- |
| `id`                   | `ClipItemId`         | UUID v7                             |
| `content`              | `Content.raw`        | 画像は空文字列、`image_path` が実体 |
| `content_hash`         | `ContentHash`        | SHA-256 hex                         |
| `type`                 | `ClipType`           | enum の文字列表現                   |
| `image_path`           | `Content` の付属情報 | 画像ファイルのローカルパス          |
| `source_app_bundle_id` | `SourceApp.bundleId` | NULL = ソース不明                   |
| `source_app_name`      | `SourceApp.name`     | NULL = ソース不明                   |
| `is_pinned`            | `ClipItem.isPinned`  | bool → integer                      |
| `is_truncated`         | `Content.truncated`  | bool → integer                      |
| `created_at`           | `ClipItem.createdAt` | Timestamp                           |
| `updated_at`           | `ClipItem.updatedAt` | Timestamp                           |

## 2. FTS5 仮想テーブル

DBML は SQLite の仮想テーブルに対応していないため、SQL で定義する。

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS clips_fts USING fts5(
    content,               -- 検索対象テキスト（clips.content と同期）
    content_id UNINDEXED,  -- clips.id への参照（インデックス対象外）
    tokenize = 'trigram'   -- 辞書不要の日本語部分一致を実現
);
```

**`trigram` を採用した理由**:
`unicode61`（デフォルト）は単語境界でトークン分割するため、日本語の部分一致が機能しない。
`trigram` は3文字単位で分割するため、辞書なしで日本語の部分一致検索が可能になる。

## 3. インデックス定義

```sql
-- 更新日時降順: FindRecent() のデフォルト表示に使用
CREATE INDEX IF NOT EXISTS idx_clips_updated_at
    ON clips (updated_at DESC);

-- ピン留め + 更新日時: ピン留めアイテムを先頭に表示する複合インデックス
CREATE INDEX IF NOT EXISTS idx_clips_is_pinned_updated_at
    ON clips (is_pinned DESC, updated_at DESC);

-- ContentHash による単件検索: FindByHash() の重複チェックに使用
-- content_hash は UNIQUE 制約があるため、このインデックスは自動生成される
```

## 4. トリガー定義

`clips` テーブルへの変更を `clips_fts` と自動同期する。
アプリケーション層はインデックスの同期を意識しなくてよい。

```sql
-- INSERT 後: FTS インデックスに追加
CREATE TRIGGER IF NOT EXISTS trg_clips_after_insert
AFTER INSERT ON clips
BEGIN
    INSERT INTO clips_fts (content_id, content)
    VALUES (NEW.id, NEW.content);
END;

-- content 更新後: FTS インデックスを更新
-- ※ kura では content は生成後に変更しない設計のため、このトリガーは安全網として定義する
CREATE TRIGGER IF NOT EXISTS trg_clips_after_update
AFTER UPDATE OF content ON clips
BEGIN
    UPDATE clips_fts
    SET content = NEW.content
    WHERE content_id = OLD.id;
END;

-- DELETE 後: FTS インデックスから削除
CREATE TRIGGER IF NOT EXISTS trg_clips_after_delete
AFTER DELETE ON clips
BEGIN
    DELETE FROM clips_fts WHERE content_id = OLD.id;
END;
```

## 5. PRAGMA 設定

アプリ起動時に以下の PRAGMA を実行する。

```sql
PRAGMA journal_mode = WAL;       -- 読み書き並行処理を可能にする
PRAGMA synchronous   = NORMAL;   -- WAL モードでのデータ安全性を保ちつつ fsync を削減
PRAGMA mmap_size     = 268435456; -- 256MB のメモリマップ I/O
PRAGMA cache_size    = -16000;   -- 16MB のインメモリページキャッシュ（負値は KB 単位）
```

## 6. データ保持ポリシー

`maxHistoryCount`（デフォルト: 10,000件）超過時に古いアイテムを自動削除する。
削除は新規 INSERT のタイミングで実行する（バックグラウンド定期実行なし）。

```sql
DELETE FROM clips
WHERE id IN (
    SELECT id FROM clips
    WHERE is_pinned = 0
    ORDER BY updated_at ASC
    LIMIT MAX(0, (SELECT COUNT(*) FROM clips WHERE is_pinned = 0) - :maxHistoryCount)
);
```

**ルール**:

- `is_pinned = 1` のアイテムは自動削除の対象外（ドメインの不変条件）。
- `maxHistoryCount` はアプリケーション層が設定コンテキストから受け取り、Repository に渡す。
